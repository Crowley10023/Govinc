This file denotes major corner stones of the security architecture.

1. Every access to backends must provide CSRF token
2. Every backend entry point must check authentication and authorization
3. The assessment direct form is allowed to be accessed without authorization and without authentication. it therefore provides a unique URL that is obfuscated.
4. Roles in the system:
    a) ADMIN: no restrictions in access
    b) Information Security Manager: Everything is accessible except all items listed in navigation under "CONFIG".
    c) Assessment Delegate: Is only allowed to see and edit assessments with himself as assigned user. Also is allowed to create new assessments.
    d) special assignment Team Lead: A team lead is allowed to see and edit all assessments of his organisational unit and its children, as well as where he is assigned as user.
       The team lead is typically assigned, when editing an organisational unit. team lead is not a standard role in the system and may not be assigned like the other roles. 
       a team lead may lead multiple organisational units.
    c) A Team Lead is allowed to see all assessments of his organisation units and their children
5. SecurityConfig.java defines what is accessible and what not. 
6. The system allows three different authentication providers: Keycloak, Azure and local. Local typically spots only the user named ADMIN with the  role ADMIN
7. Users generally may have one or more roles. valid combinations are:
    1. ADMIN and Team Lead
    2. Assessment Delegate and Team Lead
    3. Information Security Manager and Team lead
8. in Production environments, the local ADMIN user must not be active, only in development environments (see deployment)
9. A user may be deleted when the user is not in "created by" in an assessment. if deleting a user that is part of "users" of an assessment, the user must be deleted as user 
   in these assessments prior to deleting the user.
